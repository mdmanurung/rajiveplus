# Use Strict Constructors and Scoped Reader Validation

`Rajive()` result constructors should validate the complete object schema at creation time, including decomposition roles and native-missing metadata when applicable. Downstream readers should validate only the fields they actually consume, so score-only workflows can continue to use lightweight `rajive` objects while decomposition, reconstruction, and variance helpers enforce the relevant part of the block-decomposition contract. For example, `.get_block_decomp()` should validate only that `block_decomps` can supply the requested record, not that the whole object satisfies the complete `rajive` schema. `rajive_rank_only` is a separate compact internal result type with its own smaller schema; it is not a partial `rajive` object.

Constructor validation should focus on schema and shape: required slots, classes, block counts, component roles, required `u`/`d`/`v` fields, compatible dimensions, and Residual being a matrix or `NA`. Constructors should not, by default, check floating-point numeric equivalence between a stored `$full` matrix and its `u`/`d`/`v` reconstruction. Numeric equivalence checks are better kept as targeted reconstruction tests or optional diagnostics, because they are tolerance-sensitive and can be expensive on large fits. A dedicated `$full` versus `u`/`d`/`v` diagnostic helper is deferred and should be added only if a real debugging or regression-testing need appears.

Joint and Individual component records should remain plain lists in the current result schema. Constructors should validate their fields and dimensions, but should not wrap them in new per-component S3 classes for this maintainability refactor.

`rajive_incomplete` constructors should validate only top-level native-missing payload presence and shape in the constructor PR: class order, required `missing` list presence, block count alignment, and required top-level metadata groups. Deep validation of estimability, provenance, diagnostics, uncertainty, censoring, and sensitivity payload internals should be deferred to the later native-missing module split or to dedicated metadata constructors.

Constructor routing should preserve structural equivalence, not byte-level identity. The public slots, class order, names, dimensions, and accessor-visible behavior should stay unchanged; incidental attribute ordering or constructor-side normalization should not fail the refactor if the public structure is equivalent.

Result constructors should remain non-exported. They may have internal roxygen or class-schema documentation so maintainers can find the result-object contract, but they should not be added to the public API or exported from `NAMESPACE`.

Scoped reader validation does not mean permissive internals. Exported functions may translate documented compatibility behavior, but non-exported readers and reconstruction helpers should use canonical component names, validate the consumed fields, and fail with typed conditions when their required data are unavailable.

Reader and reconstruction tests should assert stable condition classes and structured condition fields where those errors become part of the internal contract. Invalid internal `block` or `component` arguments should remain ordinary internal errors. In particular, valid component-matrix requests that cannot be satisfied should signal `rajiveplus_component_matrix_unavailable` with `block`, `component`, and controlled `reason` values such as `residual_not_stored`, `invalid_component_record`, or `unsupported_component_matrix`. The `invalid_component_record` reason should remain coarse for PR-1/PR-4 and cover malformed Joint or Individual records without splitting missing fields, bad dimensions, and unsupported rank shapes into separate machine-readable reasons. The `unsupported_component_matrix` reason should mean that a valid component request reached a stored value that is not a supported matrix-producing representation; for Residual, use `residual_not_stored` for `NA` and `unsupported_component_matrix` for non-matrix, non-`NA` values.
