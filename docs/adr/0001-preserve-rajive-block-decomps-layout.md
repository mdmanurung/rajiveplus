# Preserve `rajive` `block_decomps` Layout

`rajive` objects will continue to expose the existing `block_decomps` layout as a three-role-per-data-block list matrix, with individual, joint, and residual entries stored in the established order. Internals may add named accessors and constructors to avoid repeated index arithmetic, but the returned object shape remains a compatibility contract because existing tests and downstream users can read the slot directly.

The primary internal accessor should return the stored decomposition record, for example the `u`/`d`/`v`/`full`/`rank` list or residual matrix currently present in `block_decomps`. Matrix reconstruction is a separate operation owned by a dedicated helper. This keeps object-shape access distinct from "give me a reconstructed component matrix" semantics.

The record accessor should use block-decomposition language, for example `.get_block_decomp()`. The matrix-facing helper should use component language, for example `.get_component_matrix(fit, block, component)`, because Joint, Individual, and Residual are the domain components being requested. Internal helpers should require strict 1-based integer `block` indices; any block-name resolution belongs in exported wrappers or higher-level callers before they reach the internal accessor layer. Internal `component` arguments should accept only canonical full values: `joint`, `individual`, and `residual`; abbreviations and legacy aliases stay out of internals.

These accessor helpers are implementation helpers. They should remain non-exported and use light inline comments only where helpful, rather than roxygen-generated documentation; targeted extractor tests should pin their contract.

Because the helpers are intentionally non-exported, their contract tests should call them directly from package tests, including through `rajiveplus:::` where installed-namespace tests need it. Exported wrapper behavior, including compatibility policy in `get_block_matrix()`, should be tested separately through the exported API.

PR-1 helper tests should use both fixture styles. Happy-path record identity and component-matrix reconstruction should use one tiny real `Rajive()` fit so the helpers are pinned against actual object shape. That real-fit fixture should use a fixed seed, minimal dimensions, and fixed/simple ranks or controls that avoid slow rank-selection paths where possible; the test purpose is accessor semantics, not re-testing the fitting algorithm. Strict validation, malformed records, and unavailable-matrix cases should use hand-built minimal objects so edge cases stay cheap, deterministic, and independent of the fitting algorithm.

Assertion strength should match the helper contract. `.get_block_decomp()` tests should use exact identity because the helper returns the stored record exactly. `.get_component_matrix()` tests should use exact identity only when the helper returns a stored matrix, such as stored `$full` or Residual; matrices reconstructed from `u`/`d`/`v` should use numeric equality with an explicit tolerance plus separate dimname assertions.

`.block_decomp_index(block, component, n_blocks)` should return only the flat `block_decomps` list index used by current storage and callers. It should not accept a fit object and should not return a row/column pair. `.get_block_decomp(fit, block, component)` should derive `n_blocks` from `fit$block_decomps` and pass it into the pure index helper. It should not validate the full `rajive` object schema; it should validate only the consumed `block_decomps` shape needed to read the requested record, including that `block_decomps` exists, has a length compatible with three roles per data block, and contains the requested flat index. `.block_decomp_index()` should be tested directly, not only through `.get_block_decomp()`, because it encodes the row-order convention. Tests should make the mapping obvious: within each data block, `individual` maps to offset 1, `joint` to offset 2, and `residual` to offset 3. If later refactors need matrix-coordinate semantics, add a separate helper then.

Invalid `.block_decomp_index()` arguments, including invalid `block`, `component`, or `n_blocks`, should raise ordinary internal errors. `.get_block_decomp()` is also an internal schema reader, so invalid `block` or `component` requests and invalid `block_decomps` shape should use ordinary internal errors rather than typed conditions. `.get_component_matrix()` should follow the same rule for invalid `block` or `component` arguments before it attempts reconstruction. These are programmer errors, not recoverable runtime states. Keep typed conditions for valid component-matrix requests that cannot be satisfied from the fit, such as `rajiveplus_component_matrix_unavailable` from matrix-required helpers.

Helper introduction and call-site migration should be separate changes. First add the helpers and their contract tests without migrating existing readers; then migrate direct `block_decomps` indexing in later focused changes.

`.get_component_matrix()` should be fit-owned: it returns only matrices stored in the fit or reconstructable from stored decomposition records. It should not accept original data blocks and should not compute Residual as `data - joint - individual`. Residual-from-data computation belongs in higher-level extractors that explicitly receive original blocks.

Zero-rank Joint or Individual components are available fitted components and should reconstruct to zero matrices with the correct dimensions, not to `NA` and not to unavailable-matrix errors. Unavailable-matrix errors are reserved for cases where the fit cannot supply or reconstruct a component matrix, such as an unstored Residual from `full = FALSE` or a malformed component record.

Component matrix reconstruction should preserve dimnames whenever the fit carries enough information. Stored full matrices keep their own dimnames. Matrices reconstructed from `u`/`d`/`v`, including zero-rank matrices, should use row names from `u` and column names from `v` when present.

When both `$full` and `u`/`d`/`v` are present, `.get_component_matrix()` should prefer the stored `$full` matrix. Read-side reconstruction should not perform numeric consistency checks between `$full` and `u`/`d`/`v`.

Residual remains a direct matrix or `NA` entry, not a normalized `u`/`d`/`v` decomposition record. Constructors should validate this intentionally mixed schema rather than converting Residual into a pseudo-SVD record. A future feature can revisit that only if residual scores/loadings become a real requirement.

Internal helpers that promise a component matrix should throw a typed "component matrix unavailable" error when a valid `block` and `component` request points to a stored object that cannot provide one, including an unavailable Residual from a `full = FALSE` fit. Exported compatibility functions may continue returning `NA` only where that behavior is already part of their documented public contract.

The exported `get_block_matrix()` function should become a thin policy wrapper around the internal matrix helper. It should not duplicate role indexing or reconstruction logic; it should delegate to the shared helper, preserve the public return policy where compatibility requires it, and surface the PR-0 targeted migration error for old `type = "noise"` requests.

Compatibility behavior belongs only at exported API boundaries. Non-exported callers should use the strict internal helpers directly, receive typed errors for unavailable component matrices, and never depend on legacy argument aliases or compatibility `NA` translations.

The unavailable-matrix condition should use the stable class `rajiveplus_component_matrix_unavailable`. It should carry structured fields for `block`, `component`, and `reason` so tests and callers can assert the contract without depending on exact message text. It should not be used for invalid `block` or `component` arguments. The `reason` field should be a controlled machine-readable value, initially limited to `residual_not_stored`, `invalid_component_record`, and `unsupported_component_matrix`. The `invalid_component_record` reason intentionally covers malformed Joint or Individual decomposition records broadly, including missing fields, incompatible dimensions, and unsupported rank/shape combinations; more specific details may appear in the message, but tests and callers should not branch on finer sub-reasons unless a later use case justifies expanding the reason taxonomy. The `unsupported_component_matrix` reason is reserved for valid component requests whose stored value is not a recognized matrix-producing representation. Residual `NA` should use `residual_not_stored`; a Residual entry that is neither a matrix nor `NA` should use `unsupported_component_matrix`.
